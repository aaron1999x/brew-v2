#### Database (Stage 3)
- **Migration 1 is a verbatim copy of `phase-4-system-design.md` §4** (extracted programmatically, lines 134–1116). It applied unchanged; no fixes were needed to make it run.
- **New migration `20261113000002_fix_recipe_counters.sql` (approved change in behaviour).** In §4, `create_recipe` is `security invoker` and inserts into `recipe_counters`, which has no insert policy, so **every normal member's call failed** with `new row violates row-level security policy for table "recipe_counters"` (reproduced on staging in a rolled-back transaction). Fix: a `security definer` trigger `recipes_after_insert` creates the counters row for every new recipe; `create_recipe` no longer inserts it; `copy_recipe`'s insert for the new recipe uses `on conflict do nothing`. Tested in `supabase/tests/05_counters.sql` (members can call both; each new recipe has exactly one counters row).
- **Migration order:** 1 schema · 2 counters fix · 3 storage (§7, verbatim) · 4 invite-only (roadmap §4 verbatim + prompt Appendix 2 `handle_new_user`) · 5 gear catalogue (72 rows) · 6 tombstone purge · 7 pgTAP.
- **Gear catalogue:** all 72 items from Appendix 4 kept, including Timemore Fish Smart Kettle and Varia AKU Mini (confirmed real by the owner).
- **`pg_cron` worked on staging:** extension created in `pg_catalog`; job `purge-brew-tombstones` runs daily at 19:17 UTC (03:17 MYT). The migration is guarded: if `pg_cron` can't be created it logs a notice and the migration still applies (then re-run the block by hand once it's available).
- **Supabase CLI 3.x (not the CLI the docs assume):** `supabase db push` and `supabase gen types` now target the **local** database unless `--remote` is passed, and hosted changes need `--yes`. `supabase gen types --project-id` is now `--remote=<ref>`. ⚠ `release.yml` in `release-and-versioning.md` §4 runs plain `supabase db push` with CLI `version: latest`, which would target a local database and fail; Stage 6 must account for this.
- **IPv4:** the direct database host is IPv6-only and this network has no IPv6, so `db:push` and `db:types` use the **session pooler URL** from `STAGING_DB_URL` (`--remote=<url>`), with the password passed via `PGPASSWORD`, never argv or logs. `link` is still run first, as the prompt asks.
- **`db:types` doesn't use the Management API:** `gen types --remote=<ref>` needs a token with the `database_read` permission, which the local access token lacks. Generating from the pooler URL works without Docker and without the extra scope. Output is formatted with Prettier.
- **Supabase calls the staging project "production"** in CLI output (`Target: project brew-staging … · production`). That's Supabase's label for a project's main branch, not our production project. `assert-staging` checks refs, not that label.
- **pgTAP tests:** `supabase/tests/00_helpers.sql` is included by every test file (`\ir`) right after `begin;`, so the `tests` schema, helper functions and test users are rolled back with each file. Test users use `@test.invalid`. `db-test.mjs` skips `00_helpers.sql`, runs files `NN_*.sql` in order with `psql -v ON_ERROR_STOP=1 -X -q -A -t`, fails on `not ok`, a plan mismatch or a psql error, and then checks that no `@test.invalid` auth users or allowlist rows remain. A canary file with a failing test and a wrong plan was confirmed to fail the run (then deleted).

#### App plumbing (Stage 4)
- **`proxy.ts`, not `middleware.ts`:** Next.js 16 renamed it (`src/proxy.ts`, exports `proxy`). It only refreshes the Supabase session via `lib/supabase/session.ts`, using `auth.getClaims()` (validates the JWT) and the current `@supabase/ssr` `getAll`/`setAll(cookies, headers)` API with the publishable key. The matcher skips static files, icons, `sw.js` and the manifest.
- **Error boundary props changed in this Next.js version:** `error.tsx` / `global-error.tsx` receive `{ error: unknown, retry }` (older versions: `{ error, reset }`). `ErrorPanel` focuses its heading on mount and offers Retry plus a link home (a plain `<a href="/">` on purpose, so it also works inside `global-error`).
- **Sentry v11:** `withSentryConfig` is imported from `@sentry/nextjs/config` (not the package root). Client init is `src/instrumentation-client.ts`; server and edge configs are `sentry.server.config.ts` / `sentry.edge.config.ts`, loaded from `src/instrumentation.ts`. Options live in `src/lib/sentry/options.ts`: `release: app@<version>`, `environment: NEXT_PUBLIC_APP_ENV`, `sendDefaultPii: false`, `beforeSend` strips user email/IP, cookies, headers, bodies and query strings; no performance tracing. Source maps upload only when `SENTRY_AUTH_TOKEN` is set, and also need `SENTRY_ORG` and `SENTRY_PROJECT` (added to `.env.example`; the prompt's list didn't include them). The edge config exists as asked but is unused today because the proxy runs on Node.
- **Sentry production test:** passed on production. The temporary `GET /api/sentry-test` route, `src/lib/sentry/test-key.ts` and its unit test were removed afterwards, along with `SENTRY_TEST_KEY` in `.env.example`. If it's still set on Vercel Production, unset it there too.
- **Env validation is lazy** (`getPublicEnv()` / `getServerEnv()` validate on first use, not at import), so a build or page that never touches Supabase doesn't need every variable. Invalid values throw one error listing every problem. Public variables are read by literal name so Next inlines them.
- **TanStack Query:** defaults per amendments §2 (`staleTime` 30 s, retry twice on network/5xx and never on 4xx, refetch on focus, `networkMode: 'offlineFirst'`). Mutations don't retry. Devtools render only when `NODE_ENV === 'development'`.
- **Error messages:** `lib/errors/messages.ts` maps every name the schema raises (including `invite_only`, `recipe_not_found`, `version_not_found`, `immutable_field`, `brew_version_immutable`, `cannot_suspend_self`) plus RLS refusals (`42501`), expired sessions and network failures. Unknown errors return the generic message and `isUnexpectedError()` tells callers to report them to Sentry.
- **Checks run:** `server-only` verified by temporarily importing `lib/supabase/admin.ts` from a client component (the build failed, file removed). Built app served locally against staging: `/status` showed version, commit `local`, environment, the staging host and "Database reachable"; unknown URLs return 404; `.next/static` contains no `sb_secret_`, `service_role` or `c2VydmljZV9yb2xl`. The build uses Turbopack.

#### PWA basics (Stage 5)
- **Serwist with Turbopack, no webpack needed:** `@serwist/next` is webpack-only, so it was removed. The current Serwist docs for Next.js with Turbopack use `@serwist/turbopack` (9.5.13, same version as `serwist`) plus `esbuild`: a route handler `src/app/serwist/[path]/route.ts` (`createSerwistRoute`) builds the worker at `next build` time and serves it at `/serwist/sw.js`; `SerwistProvider` in the root layout registers it; `withSerwist` wraps the Next config (inside `withSentryConfig`). `next build` stays plain (Turbopack); no `--webpack` flag.
- **Service worker source is `src/sw/sw.ts`** (outside `src/app`; it is not a route). It is deliberately minimal: precache manifest, `skipWaiting`/`clientsClaim`, one `NetworkOnly` route for page navigations and a fallback to `/~offline` for document requests that fail. **No `defaultCache` / runtime caching of data or pages** (that is M5).
- **What is precached (27 entries, ~847 KiB):** Serwist's default glob of the Next build output (`.next/static`) and `public/`, plus `/~offline` (revision = `VERCEL_GIT_COMMIT_SHA`, random locally). The offline page is a normal route (`src/app/~offline`, static, noindex).
- **`useNativeEsbuild: true` is required:** Serwist defaults to `esbuild-wasm` on non-Windows (i.e. Vercel and CI), which isn't installed.
- **The worker is registered in production builds only** (`disable` in development, so dev never serves stale caches) and `reloadOnOnline` is off. The proxy matcher skips `/serwist/*` and `/~offline`.
- **Verified in real browsers** (Playwright Chromium and WebKit against `next start`): the worker registers with scope `/`, takes control after one reload, the precache holds 27 entries, and with the network off a navigation to `/status` shows the "You're offline" page. This should become an e2e test in Stage 6.
- **Manifest** (`src/app/manifest.ts`, from `site.ts`): name, short name, `start_url: /`, `display: standalone`, colours, three icons (192, 512, maskable 512). **iOS:** `appleWebApp` metadata (capable, title, status bar), 180 px `apple-touch-icon.png` (opaque), favicon SVG.
- **Placeholder icons** come from `scripts/make-icons.mjs` (no image library; draws a filled circle in the accent colour with a white "A" and encodes the PNGs itself). Replace `public/brand/` when the real logo exists.
- **npm install scripts:** this npm blocks lifecycle scripts until approved (`npm install-scripts`). `esbuild` and `@swc/core` (a Serwist dependency) show as not approved; nothing needs them (esbuild runs from its prebuilt binary), so they were left unapproved.

#### CI, releases, backups (Stage 6)
- **Differences from `release-and-versioning.md` §4** (`release.yml`; the other files match the doc):
  - The Supabase CLI is **pinned to 3.1.0** (the version used locally; the doc says `latest`). The same pin is in `package.json` and in the CI `db` job.
  - Migrations go through the **session pooler** with a full connection URL: `supabase db push --remote="$STAGING_DB_URL" --yes` (and `$PRODUCTION_DB_URL` on release). The doc ran `supabase link` then plain `supabase db push`; in CLI 3.x that targets a **local** database, and GitHub runners have no IPv6 for the direct host. The flag is `--remote`, not `--db-url` (CLI 3.1.0 has no `--db-url` on `db push`); a dry run with the full URL (password included) was checked locally.
  - **Secrets:** `STAGING_DB_URL` and `PRODUCTION_DB_URL` (full pooler URLs) are new. `SUPABASE_ACCESS_TOKEN`, `STAGING_DB_PASSWORD` and `PRODUCTION_DB_PASSWORD` are no longer used by any workflow and can be removed. **Keep `STAGING_PROJECT_REF` and `PRODUCTION_PROJECT_REF`:** the `migrate-staging` job uses them in a guard (mirrors `scripts/assert-staging.mjs`) that fails if `STAGING_DB_URL` contains the production ref or lacks the staging ref.
- **`ci.yml`:** job `app` (typecheck, lint, `lint:tokens`, unit tests, build with dummy `sb_publishable_…` env, secret-leak grep of `.next/static` for `sb_secret_`, `service_role`, `c2VydmljZV9yb2xl`); job `db` (`supabase start` on the runner with unneeded services excluded, then `node scripts/db-test.mjs --db-url postgresql://postgres:postgres@127.0.0.1:54322/postgres` with `SKIP_ASSERT_STAGING=1`, which `assert-staging` only honours for a 127.0.0.1/localhost URL); job `e2e` (production build, `next start`, Playwright "iphone" = WebKit iPhone 15 and "desktop" = Chromium, axe in light and dark, offline service-worker test).
- **Not verifiable locally:** there is no Docker here, so the `db` job (including which services `supabase start -x …` can leave out) is checked for the first time on GitHub. If it fails, fix the exclusion list rather than the tests.
- **e2e run locally with CI's dummy env (no `.env.local`):** 16/16 passed. `/status` then shows "Database: not reachable" and still renders (as designed).
- **First release proposed 1.0.0 instead of 0.1.0 (fixed in a follow-up PR).** With no previous tag, release-please ignores the `0.0.0` in `.release-please-manifest.json` for the first release and uses its default initial version, `1.0.0`; `bump-minor-pre-major` only applies once a release exists. `release-and-versioning.md` §2/§4 assumed the manifest value would be used. Fix: `"initial-version": "0.1.0"` on the `.` package in `release-please-config.json` (a documented per-package option, read by release-please-action v4; `bump-minor-pre-major` kept). It only matters until `v0.1.0` exists; it can be left in place. The manifest stays at `0.0.0`.
