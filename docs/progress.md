#### Database (Stage 3)
- **Migration 1 is a verbatim copy of `phase-4-system-design.md` §4** (extracted programmatically, lines 134–1116). It applied unchanged; no fixes were needed to make it run.
- **New migration `20261113000002_fix_recipe_counters.sql` (approved change in behaviour).** In §4, `create_recipe` is `security invoker` and inserts into `recipe_counters`, which has no insert policy, so **every normal member's call failed** with `new row violates row-level security policy for table "recipe_counters"` (reproduced on staging in a rolled-back transaction). Fix: a `security definer` trigger `recipes_after_insert` creates the counters row for every new recipe; `create_recipe` no longer inserts it; `copy_recipe`'s insert for the new recipe uses `on conflict do nothing`. Tested in `supabase/tests/05_counters.sql` (members can call both; each new recipe has exactly one counters row).
- **Migration order:** 1 schema · 2 counters fix · 3 storage (§7, verbatim) · 4 invite-only (roadmap §4 verbatim + prompt Appendix 2 `handle_new_user`) · 5 gear catalogue (72 rows) · 6 tombstone purge · 7 pgTAP.
- **Gear catalogue:** all 72 items from Appendix 4 kept, including Timemore Fish Smart Kettle and Varia AKU Mini (confirmed real by the owner).
- **`pg_cron` worked on staging:** extension created in `pg_catalog`; job `purge-brew-tombstones` runs daily at 19:17 UTC (03:17 MYT). The migration is guarded: if `pg_cron` can't be created it logs a notice and the migration still applies (then re-run the block by hand once it's available).
- **Supabase CLI 3.x (not the CLI the docs assume):** `supabase db push` and `supabase gen types` now target the **local** database unless `--remote` is passed, and hosted changes need `--yes`. `supabase gen types --project-id` is now `--remote=<ref>`. ⚠ `release.yml` in `release-and-versioning.md` §4 runs plain `supabase db push` with CLI `version: latest`, which would target a local database and fail; Stage 6 must account for this.
- **IPv4:** the direct database host is IPv6-only and this network has no IPv6, so `db:push` and `db:types` use the **session pooler URL** from `STAGING_DB_URL` (`--remote=<url>`), with the password passed via `PGPASSWORD`, never argv or logs. `link` is still run first, as the prompt asks.
- **`db:types` doesn't use the Management API:** `gen types --remote=<ref>` needs a token with the `database_read` permission, which the local access token lacks. Generating from the pooler URL works without Docker and without the extra scope. Output is formatted with Prettier.
- **Supabase calls the staging project "production"** in CLI output (`Target: project brew-staging … · production`). That's Supabase's label for a project's main branch, not our production project. `assert-staging` checks refs, not that label.
- **pgTAP tests:** `supabase/tests/00_helpers.sql` is included by every test file (`\ir`) right after `begin;`, so the `tests` schema, helper functions and test users are rolled back with each file. Test users use `@test.invalid`. `db-test.mjs` skips `00_helpers.sql`, runs files `NN_*.sql` in order with `psql -v ON_ERROR_STOP=1 -X -q -A -t`, fails on `not ok`, a plan mismatch or a psql error, and then checks that no `@test.invalid` auth users or allowlist rows remain. A canary file with a failing test and a wrong plan was confirmed to fail the run (then deleted).
